## الهدف
جعل إدخال الدفعات السابقة واضحاً ولا لبس فيه، وإظهار المتأخرات فوراً للمستخدم.

## التغييرات

### 1) `LastPaymentSection.tsx` — ثلاث خانات بدل اثنتين
```
┌─ تاريخ آخر دفعة ──────────┐  ┌─ المبلغ المدفوع ──┐
│ 📅  5/4/2026              │  │ 80.000           │
└───────────────────────────┘  └──────────────────┘
┌─ الفترة المُغطّاة ─────────────────────────────────┐
│ من: [📅 1/3/2026]   إلى: [📅 31/3/2026]           │
└────────────────────────────────────────────────────┘
```
- الحقول الجديدة: `periodFrom` و`periodTo` (تاريخان).
- عند اختيار «تاريخ آخر دفعة» و«نمط الدفع» معروف ⇒ نملأ النطاق تلقائياً:
  - مُقدّم: من = أول شهر الدفعة، إلى = آخره.
  - مؤخّر: من = أول الشهر السابق، إلى = آخره.
- المستخدم يقدر يعدّل النطاق يدوياً (للحالات الشاذة).
- النطاق يُحدّد `opening_balance_date = periodTo + 1 يوم` (= أول دورة غير مدفوعة).

### 2) شارة متأخرات حيّة داخل النموذج
أسفل الخانات الثلاث، يحسب المكوّن فوراً (بدون حفظ) عدد الدورات وقيمة المتأخرات بناءً على `periodTo` و`rent_amount` و`rent_timing` و`today()`، ويعرض:
```
⚠ سيظهر متأخرات لـ شهرين (160.000 ر.ع) — تبدأ من أبريل 2026
```
- يستخدم لون burgundy للنص، خلفية sage-50.
- إن لم يكن هناك متأخرات: شارة sage خضراء «✓ الحساب مُسوّى حتى مارس 2026».

### 3) منطق الحفظ في `EditUnitDialog.tsx` و`NewTenancyDialog.tsx`
- `opening_balance_date` = اليوم التالي لـ `periodTo` (يمثّل بداية أول دورة غير مدفوعة، يعمل مع المؤخّر والمقدّم بنفس الطريقة).
- `last_paid_date` = تاريخ الدفعة كما هو.
- يبقى منطق `cyclesDue` في `balance.ts` بدون تغيير.

### 4) تحديث الاختبارات
- تعديل اختبارات `balance.test.ts` المرتبطة بالـ anchor (نفس النتائج، لكن الـ anchor يأتي الآن من `periodTo + 1`).
- إضافة اختبارين للحالة الجديدة:
  - مؤخّر، periodTo = 31/3/2026، الآن 24/5/2026 → cyclesDue = 1 (أبريل).
  - مُقدّم، periodTo = 30/4/2026، الآن 24/5/2026 → cyclesDue = 1 (مايو).

### 5) ترحيل البيانات (migration)
لتطبيع السجلّات القديمة على القاعدة الجديدة (`opening_balance_date = periodTo + 1`):
- مُقدّم: لا تغيير (anchor الحالي = أول الشهر التالي = صحيح).
- مؤخّر: السجلّات المُصلَحة سابقاً anchor = أول شهر الدفعة، يجب تحويلها إلى أول الشهر التالي لشهر الدفعة (= نفس قيمة المقدّم تماماً، لأن periodTo للمؤخّر = آخر الشهر السابق للدفعة، +1 = أول شهر الدفعة... خطأ).

⚠️ ملاحظة: التعريف الجديد للـ anchor يختلف بين المقدّم والمؤخّر، فإذا اعتمدنا «`anchor = periodTo + 1`» يصبح المنطق موحّداً ولا يحتاج `rent_timing` في الحساب إطلاقاً. هذا تبسيط جوهري لكنه يتطلّب:
- مراجعة `cyclesDue` ليصبح `elapsed` فقط (بدون فرع advance/arrears) لأن الـ anchor صار يمثّل «بداية أول دورة غير مدفوعة» في الحالتين.
- migration يضبط جميع الوحدات: `opening_balance_date = آخر_يوم_مغطّى + 1`.

## القرارات المطلوب تأكيدها قبل التنفيذ
1. **هل نوحّد المنطق** (anchor = periodTo+1، إزالة فرع advance/arrears من `cyclesDue`)؟ هذا الأنظف، لكن يلمس `balance.ts` ويتطلّب اختبارات أوسع.
2. **أم نُبقي المنطق الحالي** ونحوّل (periodFrom, periodTo) داخلياً إلى anchor قديم (advance: periodFrom = شهر الدفعة، arrears: periodFrom = شهر سابق)؟ تغيير أقل، لكن يبقى فرع `rent_timing` في الحساب.

أوصي بـ **(1)** لأنه يحلّ سبب البق الأصلي جذرياً ويجعل النموذج صادقاً مع المستخدم: «إلى أي تاريخ مدفوع؟» سؤال واحد لا لبس فيه.

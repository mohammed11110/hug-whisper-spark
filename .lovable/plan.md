## الهدف
إزالة الجليتش والتأخير عند **طباعة / حفظ / مشاركة** كشف الحساب والعقود والإيصالات والتقارير، خصوصًا على iPad، عبر إلغاء المسار الثقيل المشترك بدل ترقيعه.

## سبب المشكلة
المشكلة ليست في شاشة واحدة؛ أغلب الملفات تمر حاليًا عبر محرك موحّد يعتمد على:
- `html2canvas` لتحويل HTML إلى صورة كبيرة
- ثم `jsPDF` لتغليف الصورة داخل PDF
- مع `iframe/srcdoc/blob/sessionStorage` للمعاينة والطباعة

هذا المسار يسبب على iPad خصوصًا:
- استهلاك ذاكرة عالٍ
- تأخير قبل ظهور المعاينة أو ورقة المشاركة
- white/blank frames أحيانًا
- تكرار التحويل لنفس الملف عند المعاينة ثم الحفظ أو الطباعة

## ما سأبنيه
### 1) فصل أنواع الملفات حسب أفضل مسار
- **الإيصالات**: استخدام مولّد PDF مباشر السريع الموجود كأساس، مع الحفاظ على التصميم السابق بصيغة متجهة بدل snapshot.
- **كشف الحساب**: إنشاء مولّد PDF مباشر جديد بدل `buildTenantStatementHTML -> downloadHTMLAsPDF`.
- **التقارير**: إنشاء مولّد PDF مباشر جديد بدل تحويل الصفحة HTML إلى canvas.
- **العقود**:
  - العقود العامة: الاستمرار/التحويل إلى PDF مباشر حيث أمكن.
  - العقود العمانية أو القوالب الأطول: استخدام مسار HTML فقط كاستثناء منظم، وليس كافتراضي لكل الملفات.
- **الملفات المرفوعة أصلًا** (عقد/مرفق PDF أو صورة): عدم إعادة توليدها نهائيًا؛ يتم فتحها/تنزيلها مباشرة بالمسار الأصلي.

### 2) إلغاء التوليد المكرر
توحيد التنفيذ بحيث:
- **حفظ/مشاركة** = يولّد الملف مرة واحدة فقط ثم يرسله مباشرة للنظام
- **طباعة** = تستخدم نفس الـ Blob/PDF الجاهز بدل إعادة البناء
- **المعاينة** = لا تعيد التوليد إذا كان الملف نفسه جاهزًا

### 3) مسار iPad / iPhone / التطبيق الأصلي
اعتماد مسار واضح للأجهزة الحساسة:
- على iPad/iPhone/التطبيق: تسليم PDF جاهز مباشرة إلى ورقة النظام للحفظ/المشاركة/الطباعة
- تقليل الاعتماد على `window.print`, `window.open`, `srcdoc`, و`sessionStorage` للعمليات الأساسية
- إبقاء صفحة المعاينة فقط للحالات التي تحتاج preview فعلي، وليس لكل ضغطة حفظ أو طباعة

### 4) إعادة تنظيم واجهات المعاينة
- تقليل استخدام iframe داخل Dialog للملفات الكبيرة
- عند الملفات الثقيلة: فتح معاينة صفحة مستقلة أخف أو تجاوز المعاينة تمامًا إذا كان الإجراء المطلوب هو حفظ/مشاركة فقط
- إبقاء أزرار المستخدم نفسها قدر الإمكان لكن تغيير المحرك الداخلي

### 5) حالات تحميل واضحة ومنع النقرات المتكررة
- حالة `generating / saving / sharing / printing` لكل ملف
- تعطيل الزر مؤقتًا أثناء التنفيذ
- رسائل فشل واضحة مع fallback آمن
- منع تشغيل عمليتين متوازيتين لنفس المستند

- وقد أضيف helper صغير/منظم جديد داخل `src/lib/` لتوحيد استراتيجيات المستندات

## النتيجة المتوقعة
- فتح أسرع بكثير لورقة المشاركة والطباعة على iPad
- اختفاء أغلب الجليتش الناتج عن iframe/canvas
- تقليل استهلاك الذاكرة
- توحيد السلوك بين الإيصال وكشف الحساب والعقد والتقرير
- بقاء التصميم قريبًا من الحالي لكن بمحرك أخف وأثبت

## تفاصيل تقنية
```text
الوضع الحالي:
HTML -> inline fonts/images -> html2canvas -> PNG slices -> jsPDF -> share/print/preview

الوضع المستهدف:
Document data -> direct PDF builder (vector/text) -> single Blob -> save/share/print
                         \-> HTML preview only when needed
```

## ترتيب التنفيذ
1. بناء طبقة استراتيجية موحدة للمستندات داخل `pdfDocs.ts`
2. تحويل كشف الحساب والتقارير إلى PDF مباشر
3. ربط `UnitDetail` و`Payments` و`AddPaymentDialog` بالمسارات الجديدة
4. تخفيف/إعادة توجيه المعاينة في `FilePreviewDialog`
5. إبقاء fallback HTML فقط للسيناريوهات التي لا يصلح فيها التحويل المباشر
6. التحقق من سلاسة الحفظ/المشاركة/الطباعة على مسارات iOS وweb


## الهدف

رقم الإيصال يعكس بوضوح حالة الدورة:
- **دفعة كاملة من أول مرة** → رقم عادي (مثل `R-01050`).
- **دفعة جزئية أولى** → `R-01024/1`.
- **دفعات جزئية لاحقة لنفس الدورة** → `/2`، `/3`...
- **آخر دفعة تكمل الدورة** → `/D` (Done) بنفس الرقم الأساسي.

اللاحقة مرتبطة بـ (نفس الوحدة + نفس فترة الإيجار `period_start`/`period_end`) حتى تظهر دفعات الدورة الواحدة متسلسلة في كشف حساب الوحدة.

## المبدأ (الأبسط والأوضح)

نحتفظ بـ `receipt_number` كنص واحد كما هو الآن (مثل `"R-01024/1"` أو `"R-01050"`). لا أعمدة جديدة، لا migration. الربط بين دفعات الدورة الواحدة يحصل برمجياً عبر `unit_id + period_start + period_end`.

### لماذا هذا الخيار:
- **أبسط** — لا تغيير على schema.
- **واضح للمستخدم** — الرقم نفسه يحكي القصة (`/1` يعني «أول جزء»، `/D` يعني «الدورة أُغلقت»).
- **مرتبط بالوحدة تلقائياً** — كشف حساب الوحدة يجمع دفعات نفس الدورة بمجرد المطابقة على الفترة.

## منطق توليد الرقم (عند إضافة دفعة جديدة)

في `AddPaymentDialog.tsx` بعد حساب `cycleDue` و`amount` المُدخل:

```
1) جلب دفعات سابقة لنفس (unit_id + period_start + period_end) غير المحذوفة.
2) حساب: sumPaidBefore = مجموع amount لتلك الدفعات.
   isFirstInCycle = (الدفعات السابقة فارغة)
   willClose = (sumPaidBefore + amount) >= cycleDue - 0.009
   isPartial = !willClose
   willCompleteSplit = (!isFirstInCycle && willClose)
   wasSplit = (!isFirstInCycle) // كانت هناك دفعات سابقة جزئية

3) تحديد الرقم:
   - حالة A: isFirstInCycle && willClose  → رقم جديد بدون لاحقة (R-01050)
   - حالة B: isFirstInCycle && isPartial  → رقم جديد + "/1" (R-01024/1)
   - حالة C: wasSplit && isPartial        → نفس الرقم الأساسي + "/n+1"
   - حالة D: wasSplit && willClose        → نفس الرقم الأساسي + "/D"
```

**الرقم الأساسي** = الجزء قبل `/` من أول إيصال في الدورة (مثل `R-01024` من `R-01024/1`).

**عداد الإيصال (`bumpReceiptNumber`)** لا يُستدعى إلا في الحالات A و B (إصدار رقم جديد). الحالات C و D تعيد استخدام الرقم الأساسي السابق.

## التغييرات الفعلية (ملفان فقط)

### 1) `src/components/AddPaymentDialog.tsx`

- قبل الحفظ: استعلام بسيط عن `payments` بنفس `unit_id` و`period_start` و`period_end` و`deleted_at IS NULL`.
- استبدال منطق توليد `receipt_number` الحالي بالخوارزمية أعلاه.
- استدعاء `bumpReceiptNumber` فقط في الحالات A و B.
- إذا كانت الدفعة بدون دورة (`period_start = null`) → السلوك الحالي بدون تغيير (رقم عادي).

### 2) `src/components/EditPaymentDialog.tsx`

- منع تعديل `receipt_number` يدوياً إذا كانت الدفعة جزءاً من دورة مجزّأة (لاحقتها `/n` أو `/D`)، لتجنّب كسر التسلسل.
- عند تعديل المبلغ: إذا تغيّرت حالة «الإغلاق» (مثلاً دفعة كانت `/2` وأصبحت تكمل الدورة) → عرض تنبيه فقط، بدون إعادة ترقيم تلقائي (لتفادي تعقيدات).

### 3) عرض الإيصال (`src/pages/Payments.tsx` — `buildReceiptHTML`)

- الرقم يُعرض كما هو من DB (يتضمن اللاحقة).
- إضافة سطر معلوماتي صغير تحت رقم الإيصال عند وجود لاحقة:
  - `/1`، `/2`... → AR: «دفعة جزئية ٢ من دورة قيد التحصيل» / EN: "Partial payment 2 — cycle in progress"
  - `/D` → AR: «الدفعة الختامية — الدورة مسدّدة بالكامل» / EN: "Final payment — cycle fully settled"
- شارة الحالة:
  - لاحقة `/n` بدون `/D` → شارة برتقالية «جزئي / Partial»
  - `/D` أو بدون لاحقة → شارة خضراء «مسدّد / Paid»

### 4) كشف حساب الوحدة (`src/pages/UnitDetail.tsx`)

- تجميع الدفعات حسب الدورة (`period_start + period_end`).
- داخل كل مجموعة: ترتيب حسب `payment_date`، عرض اللاحقة بجانب الرقم.
- مجموعة الدورة المكتملة (تحتوي `/D` أو دفعة كاملة بلا لاحقة) → خلفية خفيفة sage.
- مجموعة الدورة المفتوحة (آخر إيصال `/n` بدون `/D`) → خلفية terracotta خفيفة + سطر «متبقي للدورة: X ر.ع».

## خارج النطاق

- لا تغيير على schema قاعدة البيانات.
- لا تعديل على منطق التوزيع التلقائي للمتأخرات.
- لا تغيير على `pdfDocs.ts`.
- الدفعات القديمة (قبل هذا التحديث) تبقى بأرقامها الحالية — المنطق الجديد يطبَّق على الدفعات الجديدة فقط، والعرض في كشف الحساب يتعامل مع كلا النوعين بأمان.

## النتيجة المتوقعة

- المستأجر دفع ١/١: ١٠٠ من إيجار يناير (٢٠٠) → `R-01024/1` (شارة جزئي).
- إيصالات وحدات أخرى خلال الشهر تتسلسل عادياً... `R-01049`.
- المستأجر دفع ١/٢: ٣٠٠ → النظام يُنشئ:
  - `R-01024/D` لإغلاق يناير بـ ١٠٠ (شارة مسدّد، سطر «الدفعة الختامية»).
  - `R-01050` لكامل فبراير ٢٠٠ (رقم عادي، شارة مسدّد).
- كشف حساب الوحدة يُظهر دورة يناير كمجموعة واحدة `R-01024/1` + `R-01024/D` تحت بعض، وفبراير منفصلة.
